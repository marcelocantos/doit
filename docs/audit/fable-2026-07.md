## Architecture (as mapped during the audit)

doit is an MCP (stdio) server that mediates command execution for Claude Code. cmd/doit/main.go builds one engine.Engine and registers ~20 MCP tools via mcptools/mcptools.go (doit_execute, doit_dry_run, doit_approve, session/audit/policy tools). The agent-facing hot path is handleExecute: it calls Engine.Evaluate (dry policy), and on "escalate"/"deny"(bypassable) fires an MCP *elicitation* to a human (allow_once/allow_always/deny/deny_always); on approval it re-runs Engine.Execute with Retry=true, optionally records an L2 entry and offers Starlark rule promotion. Actual execution is always `sh -c <command>` — doit deliberately does NOT parse shell composition; the design delegates compound/obfuscated commands to the L3 LLM. Engine.Execute/ExecuteStreaming route through evaluatePolicy → runShellCommand and write an audit entry.

The policy chain (internal/policy) is three tiers evaluated in evaluatePolicy (engine/engine.go:1521): L1 deterministic (Go rules in level1.go + Starlark via internal/starlark), then L2 learned YAML store (level2.go, only Approved entries), then L3 two-tier LLM cascade (level3.go: fast sonnet → deep opus) invoked as one-shot `claude -p` (internal/llm/client.go). Each layer returns Allow/Deny/Escalate; only a definitive result stops the chain, otherwise it escalates downward. A pre-policy "script gate" (engine handleScriptGate + internal/script) intercepts plain `bash foo.sh`/`./foo.sh` invocations and gates them by SHA-256 content hash approval, bypassing L1/L2/L3. Approval tokens for L3 escalations are single-use, TTL-bound, args-bound, held in-memory (internal/policy/tokens.go). A separate reversibility feature (internal/cap TierEvaluator, rm.go) computes an "effective tier" but — see invariants — it is only used to label audit entries.

Concurrency model: the engine serves concurrent MCP tool calls. Shared mutable state is guarded piecemeal: audit.Logger has its own mutex serialising appends; TokenStore and script.Store have mutexes; the engine uses l1Mu/l2Mu/sessionMu RWMutexes for policyL1, policyL2, and session. policyL3/tokenStore/durationStore/projectCtx are set once at construction and read lock-free. Background auto-promotion (tryPromote, single-flighted via promoteCh) and duration learning read the audit log and load-modify-save the L2 YAML store off the request goroutine. Timeouts use context.WithTimeout with a process-group SIGKILL (procgroup_unix.go).

Persistence is file-backed: hash-chained JSONL audit log (internal/audit, ~/.local/share/doit/audit.jsonl), YAML L2 store and script-approval store (atomic temp+rename), YAML config (~/.config/doit/config.yaml) with tighten-only per-project overlay (internal/config MergeProject). Note the MCP server constructs the engine WITHOUT ProjectRoot, so per-project config overlay and project-context safe-command rules never activate in the server binary; they only apply to external library consumers (e.g. jevon) that pass ProjectRoot.

## Load-bearing invariants

- Every executed command must pass a binding policy decision; an Escalate/uncertain result must fail CLOSED. VIOLATED: engine.Execute (engine.go:752) only special-cases Deny and Escalate-with-Level==3; an Escalate result at Level 1 or 2 (which is what remains when L3 is disabled or e.policyL3 is nil) falls through both guards and EXECUTES the command. Fail-open default.
- Tier gating and the hardcoded argument RuleSet must actually block execution. VIOLATED: Registry.CheckTier and Registry.CheckRules (incl. rules.Hardcoded()) are defined but never called anywhere on the exec path; EffectiveTier is computed only to populate the audit `tiers` label. 'dangerous tier disabled' (config default, advertised by doit_check_config §4) provides no runtime enforcement.
- L1 catastrophic/deny rules must catch the dangerous operation regardless of how it is spelled. VIOLATED by design surface: all L1 rules key on strings.Fields(command)[0], so `x && rm -rf /`, `cd d; rm -rf ~`, `/bin/rm -rf /`, `command rm -rf /`, `eval`, `$(...)` bypass checkRmCatastrophic and config flag-rules; and `rm --recursive --force /` bypasses even the direct case (HasAnyFlag only maps -r/-R, not --recursive).
- The audit hash chain on disk must be gap-free and each entry's prev_hash must reference the previously persisted entry. RISK: logger.Log (audit/logger.go:102,142) increments l.seq and advances l.prevHash BEFORE the file write; a failed/partial write leaves in-memory state ahead of disk, producing a permanent sequence gap or an orphaned prev_hash that Verify rejects forever, with no rollback.
- Once the audit log exists and is non-empty, NewLogger must resume seq/prevHash from the true last entry. RISK: NewLogger only Unmarshals the final line; if that line is corrupt/partial it silently leaves seq=0/prevHash=genesis, so subsequent writes restart at seq 1 and re-chain from genesis, colliding sequence numbers and forking the chain.
- Every allowed execution must be recorded in the audit log. VIOLATED: after the size limit is hit, logger.Log returns (0,nil) and commands keep executing UNLOGGED with no error surfaced to the caller (logger.go:98-100).
- An approval token authorises exactly one human-approved action and cannot be self-issued by the agent. RISK: escalation tokens are auto-issued by the engine (Execute) with no human in the loop at that layer, and are surfaced to the caller as escalate_token via buildResult whenever MCP elicitation is unavailable/errors — letting the agent replay the token to run the escalated command.
- Script content that is executed must equal the content that was hash-approved. RISK (TOCTOU): the gate hashes inv.ResolvedPath then later runs `sh -c` which re-reads the file; the file (agent-controlled) can change between hash and exec. resolveScriptPath also does not resolve symlinks.
- The L2 learned-policy YAML store must not suffer lost updates. RISK: RecordDecision and background tryPromote both do load-modify-save via AppendEntries with no shared lock (and no cross-process lock), so concurrent writes can drop entries.
- Audit-chain verification must never crash on adversarial input. VIOLATED: Verify slices entry.PrevHash[:16] and entry.Hash[:16] (verify.go:41,47); a tampered/truncated line with a short or empty hash field triggers an index-out-of-range panic, crashing doit_audit_verify instead of reporting the tamper.

## Trust boundaries

- MCP tool arguments from the agent (mcptools.go handleExecute/handleDryRun/etc.): command, justification, safety_arg, cwd, approved token, timeout/expected_duration, project_root, filename — all attacker-influenced and flow into sh -c, policy, token validation, and file reads.
- The command string itself → `sh -c <command>` in engine.runShellCommand/runScriptCommand: full shell interpretation (composition, expansion, subshells) happens AFTER policy, which only inspects the first token — the core TOCTOU/normalization boundary.
- Approval tokens submitted as req.Approved / doit_approve args, validated in TokenStore.Validate against args equality (tokens.go); single-use consumption interacts badly with the two-step approve→execute flow.
- The audit log file on disk (internal/audit read paths: Verify, Query, QueryLatest, Tail, and tryPromote/duration learning): parsed as untrusted JSONL — malformed lines silently skipped (Query) or panic (Verify), and its contents drive auto-promotion of L2 policy.
- Global and per-project YAML config (internal/config Load/LoadProject/MergeProject) and the L2 learned-policy YAML store and script-approval YAML (internal/policy/store.go, internal/script/store.go): loaded and trusted; writability of their directories is the whole safety perimeter (doit_check_config §5).
- Starlark rule files in starlark_rules_dir (internal/starlark LoadDir) executed as L1 policy — anyone who can write that dir controls allow/deny decisions.
- doit_repo_read filename + project_root (internal/context/reporead.go ReadRepoFile): allowlist + separator checks, but project_root is attacker-supplied and symlinks under it are not resolved.
- The L3 LLM prompt: agent-supplied command/cwd/justification/safety_arg and agent-supplied session scope/description are interpolated into the gatekeeper prompt (level3.go buildPrompt/buildSessionPrefix) — prompt-injection boundary, mitigated only by xmlEscape + instruction text.
- Environment map (req.Env) and cwd merged into exec.Cmd for the child shell; child inherits filtered os.Environ (llm client strips CLAUDECODE* only for the claude subprocess, not for executed commands).

## Strategic recommendations

SYSTEMIC THEME — the policy layer is fail-OPEN, and its strongest-looking defenses are decorative. doit is a security-mediation gateway whose whole reason to exist is "every executed command passes a binding decision, and uncertainty fails closed." Three independent, mutually-reinforcing defects invert that guarantee, and I confirmed each in source:

1. Escalate falls through to execution (engine/engine.go:779). Execute only intercepts Deny, and Escalate strictly when `Level==3 && tokenStore!=nil`. Every other Escalate — L1, L2, or L3 when policyL3 is nil / tokenStore is nil / L3 disabled — drops past both guards to "Execute the command" (line ~812). Since the chain "escalates downward" and terminates in Escalate whenever no tier gives a definitive Allow/Deny, the default outcome for any command the deterministic tiers don't recognize, in any deployment without a live L3, is: run it. This is the single most important finding: the failure mode is not an edge case, it is the configuration's resting state.

2. The advertised enforcement (cap tier gating + hardcoded arg RuleSet) is never wired to the exec path. `CheckTier`/`CheckRules` have zero callers outside tests (confirmed by grep); `EffectiveTier` is invoked only at engine.go:1552 to populate the audit `tiers` label. So `doit_check_config §4`'s "dangerous tier disabled" and the hardcoded `rm`/`dd`/etc. RuleSet describe a control that does not run. Dead safety code is worse than absent safety code: it manufactures operator confidence and shows green in the config self-report while enforcing nothing.

3. Policy inspects a different artifact than the shell executes. All L1 rules key on `strings.Fields(command)[0]`, but execution is always `sh -c <command>` with full composition/expansion applied AFTER the decision. `x && rm -rf /`, `cd d; rm -rf ~`, `/bin/rm`, `command rm`, `eval`, `$(...)`, and even `rm --recursive --force /` (HasAnyFlag maps only -r/-R) bypass the catastrophic-rm and flag rules. The design consciously delegates composition to L3 — but combined with defect 1, when L3 is nil the composed-command path both evades L1 AND fails open. The two "acceptable in isolation" design choices compose into a catastrophic gap.

The correct principal-engineer instruction: treat the policy chain as a total function that MUST terminate in an explicit Allow or Deny. Any Escalate that reaches Execute without a live human-gate handler must be converted to Deny (fail closed) — that one change closes defect 1. Then either wire CheckTier/CheckRules into evaluatePolicy or delete them and stop advertising the tier (defect 2). For defect 3, decide explicitly: either normalize/decompose the command before policy, or make "command is compound/obfuscated" a mandatory-escalation trigger that fails closed when no human gate exists — never a silent pass.

SECONDARY THEME — token self-issuance defeats the human-in-the-loop. Escalation tokens are minted by the engine itself (`tokenStore.Issue`, engine.go:781) with no human at that layer, and surfaced back to the agent as `EscalateToken`/`approval-token:` in stderr. When MCP elicitation is unavailable or errors, the agent that requested the dangerous command receives the very token that authorizes it and can replay it via doit_approve. The token machinery (single-use, TTL, args-bound) is well-built but its trust anchor is wrong: the entity being gated is handed the key. Tokens must only be issued as the result of a human elicitation decision, never returned to the caller on the elicitation-unavailable path.

CROSS-CUTTING THEME — the audit chain is tamper-EVIDENT but neither durable nor gap-free, so it cannot be trusted as the security-of-record it is designed to be (and which auto-promotion of L2 policy depends on). Confirmed in logger.go: (a) `l.seq++` and `l.prevHash = entry.Hash` advance in memory BEFORE the file write and there is no rollback on write error, and there is no fsync anywhere in internal/audit — a torn/failed write leaves in-memory state ahead of disk, creating a permanent gap or orphaned prev_hash that Verify rejects forever; (b) NewLogger resumes from only the last line and, if that line is corrupt/truncated (the exact residue of (a) or a crash), silently restarts at seq=0/genesis, forking a second genesis-rooted sub-chain with colliding sequence numbers and no startup signal — this is the one finding that survived full two-lens verification; (c) once the size limit trips, Log returns (0,nil) and commands keep executing UNLOGGED with no error to the caller. Because tryPromote and duration learning read this same log to load-modify-save the L2 store, corruption/gaps here silently propagate into future policy. The fix set is coherent: write-then-advance (or advance-then-rollback-on-error) + fsync on security-critical entries + robust backward-scan resume that errors loudly rather than resetting + never-silent-drop on size limit. Also harden Verify itself — it slices `PrevHash[:16]`/`Hash[:16]` and panics on a short/empty hash from a tampered line, meaning adversarial input crashes the verifier instead of reporting tamper.

CONCURRENCY / STATE THEME — shared mutable state is guarded piecemeal, and the gaps are on write paths. RecordDecision (request goroutine) and background tryPromote both do unsynchronized load-modify-save of the L2 YAML via AppendEntries; concurrent writes lose entries, and there is no cross-process lock at all. policyL3/tokenStore/durationStore/projectCtx are read lock-free on the assumption they are construction-immutable — fine today but a latent trap for any future setter. Recommend a single L2 store mutex (or serialize all L2 mutation through the promoteCh single-flight) and a documented "immutable after construction" contract on the lock-free fields.

TOCTOU / NORMALIZATION THEME (the recurring root cause). The script gate hashes `inv.ResolvedPath` then later `sh -c` re-reads the file — agent-controlled content can change between approval and exec — and resolveScriptPath does not resolve symlinks; doit_repo_read likewise trusts an attacker-supplied project_root and does not resolve symlinks under it. This is the same class as defect 3: the system validates a snapshot/representation and then acts on a freshly-resolved, mutable, agent-influenced reality. Systemic remedy: resolve-once (open fd / realpath, resolve symlinks), hash the bytes you will actually execute, and pass that same handle to exec — close the TOCTOU window structurally rather than per-feature.

TRUST-BOUNDARY POSTURE. The whole safety perimeter reduces to filesystem writability of a few dirs: the L2 store, script-approval store, global/project YAML config, and especially starlark_rules_dir (arbitrary allow/deny logic executed as L1). Anyone who can write those directories owns policy. This should be stated as an explicit, documented threat-model assumption with directory-permission checks enforced at startup (doit_check_config §5 reports it but does not enforce). Separately note the server/library asymmetry: main.go constructs the engine WITHOUT ProjectRoot, so per-project tighten-only overlay and project-context safe-command rules never activate in the shipped server — only external consumers (jevon) that pass ProjectRoot get them. Any reasoning about "project config hardening" is inapplicable to the server binary, and that discrepancy should be documented so operators don't assume protection they don't have.

PRIORITIZATION for the next engineer: (1) make Escalate-without-live-handler fail closed — highest leverage, smallest diff, closes the resting-state bypass; (2) stop returning escalation tokens to the agent; (3) either enforce or delete CheckTier/CheckRules and reconcile doit_check_config's claims with reality; (4) audit durability + loud resume + no-silent-drop; (5) decide the compound-command policy explicitly; (6) L2 write serialization; (7) TOCTOU/symlink hardening; (8) panic-proof Verify.

### F1 — [CRITICAL] Escalate/uncertain policy results fail OPEN — Execute runs the command instead of blocking

- **Location:** `engine/engine.go:779`
- **Dimension:** -
- **Invariant violated:** Every executed command must pass a binding policy decision; an Escalate (uncertain) result must fail CLOSED (block or route to a human), never execute.
- **Failure scenario:** Set config `policy.level3_enabled: false` (a documented, test-covered configuration — see engine/engine_test.go:21 and mcptools/elicitation_audit_test.go:280). Then policyL3 and tokenStore are BOTH nil (engine.go:274-315). Call Execute with any command not matched by an L1/L2 rule, e.g. `touch /tmp/PWNED && echo hi`: L1 returns {Escalate,Level 1} ("no deterministic rule matched"), L2 returns {Escalate,Level 2} ("no learned policy"), L3 is skipped (policyL3 nil), so evaluatePolicy returns {Escalate,Level 2}. In Execute, pResult is not Deny, and the guard `Decision==Escalate && Level==3 && tokenStore!=nil` is false (Level is 2 and tokenStore is nil), so control falls straight through to `e.runCommand` at line 815 and the command EXECUTES with exit 0. Reproduced: the marker file was created and stdout captured `hello-from-unapproved-command`, with res.PolicyDecision=="escalate". This also hits library consumers who call Execute directly (Execute never elicits), AND the default L3-enabled MCP server whenever the client lacks elicitation capability: handleExecute (mcptools/mcptools.go:301-305) catches the elicitation error and calls executeAndRespond->Execute; its comment claims this "will return the denial", which is false for an escalate decision. ExecuteStreaming has the identical defect at engine.go:867.
- **Evidence:**

```
if pResult.Decision == policy.Escalate && pResult.Level == 3 && e.tokenStore != nil {
			... issue token, return ...
		}
		wasL3 = pResult.Level == 3
		...
	}
	// Execute the command.
	exitCode, auditSeq := e.runCommand(ctx, args, req, &stdoutBuf, &stderrBuf)
```

- **Fix sketch:** In Execute and ExecuteStreaming, treat any non-Allow decision as terminal: after the Deny branch, replace the narrow `Escalate && Level==3 && tokenStore!=nil` check with `if pResult.Decision != policy.Allow { log, issue a token if tokenStore!=nil else return exit 1, and RETURN }`. Never reach runCommand on Escalate. Correspondingly, the mcptools.go:304 elicitation-error path should return an error (fail closed), not executeAndRespond.
- **Verification:** Repro (already run) at /private/tmp/claude-501/-Users-marcelo-think/d9b0c9f7-c002-4328-aa22-81d64543a94d/scratchpad/audit-repro/failopen (go.mod replaces the repo). Or add an engine unit test: build an engine from a config with level3_enabled:false, call Execute on a novel command, assert ExitCode!=0 and that no side effect occurred. BEFORE fix: marker created, exit 0. AFTER fix: no marker, exit 1.

### F2 — [HIGH] Dry-run Evaluate consumes the single-use approval token, so doit_execute(approved=…) always denies the escalated command

- **Location:** `engine/engine.go:1528`
- **Dimension:** -
- **Invariant violated:** A valid, unexpired approval token presented with its bound command must authorise exactly one execution of that command.

```

	_, err := e.tokenStore.Validate(req.Approved, args)   // engine.go:1528 — reached by BOTH Evaluate (dry-run) and Execute; Validate deletes the token (tokens.go:81)

// mcptools.go:274  evalResult := eng.Evaluate(ctx, r)   // r carries Approved -> burns token before Execute runs
```

- **Fix sketch:** Make token consumption happen only on the real execution path, not the dry-run. Either (a) add a non-consuming Peek/Check used by Evaluate and only consume inside Execute, or (b) have handleExecute skip the Phase-1 Evaluate when req.Approved != "" and go straight to Execute, or (c) carry the validated TokenEntry from the single Evaluate into Execute so Validate runs once. Note: whichever fix is chosen, also address Finding 3 first — making Evaluate non-consuming without gating self-issuance opens agent replay in the MCP path.

### F3 — [HIGH] Engine self-issues escalation tokens with no human step and returns them to the caller; a direct Engine.Execute consumer can replay the token to self-approve the escalated command

- **Location:** `engine/engine.go:781`
- **Dimension:** -

(Currently the MCP binary happens to fail closed only because Finding 1's double-consume denies the replay — fixing Finding 1 naively activates this bypass in the server.)
- **Evidence:**

```
if pResult.Decision == policy.Escalate && pResult.Level == 3 && e.tokenStore != nil {
	token, tokenErr := e.tokenStore.Issue(strings.Join(args, " "), args)  // engine.go:781 — no human in the loop
	...
	return &Result{ ... EscalateToken: token }  // engine.go:797

// mcptools.go:571-572  resp["escalate_token"] = result.EscalateToken  // handed straight to the agent
```

- **Fix sketch:** Do not treat an engine-issued escalate_token as authorization. Tokens should be minted only by the human-approval step (elicitation accept), tagged with a provenance/human flag, and evaluatePolicy should reject tokens lacking that flag. After fix: a token not carrying human provenance must be rejected by evaluatePolicy.

### F4 — [HIGH] Logger.Log advances seq/prevHash before the file write and never rolls back on failure, permanently breaking the chain

- **Location:** `internal/audit/logger.go:102`
- **Dimension:** -
- **Invariant violated:** The on-disk hash chain must be gap-free: each persisted entry's seq == prev+1 and its prev_hash must equal the hash of the previously persisted entry. In-memory chain state must not advance past what is durably written.
- **Failure scenario:** State is seq=N, prevHash=H_N. A Log call increments l.seq to N+1 and sets l.prevHash=H_{N+1} (lines 102,142) BEFORE opening/writing the file. If OpenFile (line 150) or f.Write (line 156) fails (audit file/dir made read-only, disk full, or a partial write returning n<len), the entry is not persisted but l.seq and l.prevHash are already advanced with no rollback. Every caller in engine.go discards the returned error (e.g. engine.go:726,746,1784 use `_, _ =`), so the failure is silent. The next successful Log writes Seq=N+2 with PrevHash=H_{N+1} (an orphan whose entry was never written). audit.Verify then permanently reports `sequence gap: expected N+1, got N+2` and a prev_hash mismatch — a false tamper alarm caused by an ordinary transient write error, with a real, unexplained gap in the record of executed commands.
- **Evidence:**

```
l.seq++  // line 102 ... entry.Hash = computeHash(entry); l.prevHash = entry.Hash  // line 142 ... f, err := os.OpenFile(...); if _, err := f.Write(data); err != nil { return 0, fmt.Errorf("write audit entry: %w", err) }  // lines 150-158, no rollback
```

- **Fix sketch:** Compute the candidate entry using nextSeq := l.seq+1 and prevHash into locals; marshal and write to the file FIRST; only after a successful write assign l.seq = nextSeq and l.prevHash = entry.Hash. On any write error, leave l.seq/l.prevHash untouched and return the error. Additionally, have engine.go callers surface/log the Log error instead of discarding it (`_, _ =`).
- **Verification:** Before: NewLogger+Log N entries; chmod the audit file to 0400; call Log (fails at OpenFile but advances state); chmod back to 0600; call Log again; audit.Verify -> reports a sequence gap / prev_hash mismatch. After fix: repeat -> the failed Log returns an error and leaves state unchanged; the subsequent Log writes Seq=N+1 with PrevHash=H_N and audit.Verify passes.

### F5 — [HIGH] doit_audit_verify panics (crashes) instead of reporting tamper when an entry has a short/empty hash field

- **Location:** `internal/audit/verify.go:41`
- **Dimension:** -
- **Invariant violated:** Audit-chain verification must never crash on adversarial/corrupt input; a tampered or truncated entry must be reported as a violation, not defeat the verifier.
- **Failure scenario:** An attacker or a partial write leaves a line in ~/.local/share/doit/audit.jsonl such as {"seq":2,"prev_hash":"x","hash":"","ts":"..."}. Verify unmarshals it (empty/short strings are valid JSON), reaches the prev_hash-mismatch branch (entry.PrevHash != expectedPrev) at line 41 and evaluates entry.PrevHash[:16]; with PrevHash="x" this is a slice-out-of-range panic. Likewise line 47 (entry.Hash[:16]) panics when the tampered entry has a short/empty hash. Because handleAuditVerify calls audit.Verify directly, doit_audit_verify crashes with 'slice bounds out of range [:16]' rather than returning 'Audit chain violation', so the one tool meant to detect tampering is disabled by the very tampering it should catch.
- **Evidence:**

```
return fmt.Errorf("line %d: prev_hash mismatch: expected %s, got %s", i+1, expectedPrev[:16]+"...", entry.PrevHash[:16]+"...")  // line 41; and line 47: computed[:16]+"...", entry.Hash[:16]+"..."
```

- **Fix sketch:** Add a helper `func short(s string) string { if len(s) < 16 { return s }; return s[:16] }` (or use fmt with a width) and use short(expectedPrev), short(entry.PrevHash), short(entry.Hash), short(computed) in the two Errorf calls. The computed/expectedPrev values are always full hashes, but the entry-derived fields are untrusted and must be clamped.
- **Verification:** Before: create a valid log via NewLogger+Log, append a line with "hash":"" (or prev_hash of length <16), call audit.Verify(path) -> it panics (reproduced: `slice bounds out of range [:16] with length 0`). After fix: the same call returns a non-nil error like `line N: hash mismatch: ...` and does not panic. Add a unit test asserting Verify returns error (not panic) for a short-hash line.

### F6 — [HIGH] doit_repo_read follows symlinks and accepts an arbitrary project_root, defeating the read allowlist

- **Location:** `internal/context/reporead.go:63`
- **Dimension:** -
- **Invariant violated:** The gatekeeper may only read the narrow allowlist of manifest/config files, and the resolved path must remain within projectRoot (per the function's own doc: 'The resolved path is verified to remain within projectRoot' and 'No executable code files ... are allowed').
